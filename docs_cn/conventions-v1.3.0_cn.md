# Transnet 约定

版本：1.3.0

本约定版本独立于应用版本。1.3.0 版增加所属接口字段、首次使用指南顺序、统一可观测性与发布记录；旧版可从 Git 历史查阅。

本约定适用于整个仓库；新的版本化约定只有在更新仓库引用后才会取代本文件。docs 下的组件专属文档与本文件冲突时，仅在该组件范围内以组件文档为准。

## 行内文档

注释应简短，紧邻相关代码。仅说明名称与类型无法表达的约束、归属、安全、并发或意外故障；不要为了覆盖每个公开项目而添加套话。Rust 使用 `//!` 说明有价值的模块约束，使用 `///` 说明非显而易见的公开契约。调用方需要时说明不安全契约与可失败行为。代码注释使用英文；行为改变时修正过时说明。

## Markdown 文档

Markdown 正文可以超过代码行宽目标。除非包含嵌套块或围栏代码，段落和简单列表项都保持在一个物理行。优先使用短段落和段落间隔；列表只用于真实枚举、检查清单和流程。

关系图、流程和架构使用 Mermaid。不要使用 ASCII 图。简单映射不要使用小型双列表格，改写为 source -> target 或 key: value。文风应像内部工程笔记：一段一个观点、没有填充语，只选择性使用粗体强调。

文档中应尽量少用行内反引号。反引号只用于精确标识符、线协议字段、命令、路径、值和语法；普通正文、标题和解释性术语使用纯文本。围栏代码块内的精确代码不受此限制。

公开项目仍应保留代码注释。docs 用于架构、契约、运维和产品文档；不要直接编辑生成文档，应更新源注释或手写 Markdown 后再生成。

需要时，每个公开模块只有一份手写 Markdown 文档。简单文档可以自由且精简；建议使用 Contents、Overview、Architecture、API、Design 和 Testing 的结构仅供参考，不应机械套用。标题、顺序和深度须按具体仓库和文档目的调整。

### 文档结构

使用 `docs/documentation-index.md` 作为全仓库入口。它链接权威系统设计、接口目录、模块参考目录与任务指南，不重复其内容。凡包含多个可独立使用页面的文档目录，都必须有一个索引或目录，说明该目录范围，并用一句话描述和链接每个所属页面。

按权威归属放置文档：

- `docs/transnet.md`：产品语义与系统架构。
- `docs/product/`：展开系统设计但不重新定义合同的消费者可见行为。
- `docs/interfaces/`：规范 HTTP、UDS 与存储 adapter 线上合同，按服务边界或路由领域分组。
- `docs/reference/<module>.md`：只有一个文档关注点的模块使用一份面向实现的参考页。
- `docs/reference/<module>/`：只有当模块存在多个可独立使用的文档关注点时才放置聚焦内页。
- `docs/guides/`：开发、配置、发布和质量保证等面向任务的操作步骤。

重要模块或稳定子系统应拥有一份实质文档。当它是该模块唯一页面时，直接放在 `docs/reference` 下；禁止只有一个文件的目录。只有当模块包含多个可独立搜索的页面，并且每页都有足够独特的设计、生命周期、不变量或验证指导可独立成立时，才创建模块目录。紧密耦合的关注点保持在一起；不得按每个源文件、类型、路由或假设未来模块创建页面。

不得保留简短占位页、重复边界套话，或只罗列索引或源码模块已显而易见职责的页面。此类内容应合并到模块主文档或源码注释。页面数量及文档与源码文件一一对应都不是目标；清晰归属与有用搜索结果才是目标。

每项事实只有一个权威位置。参考页解释模块所有权、依赖、生命周期、不变量、当前/目标状态与验证；精确字段和示例链接接口文档，流程链接指南，产品语义链接系统设计，项目级 API 细节链接 rustdoc。摘要必须简短，不得在同级页面之间复制整份合同、字段目录、测试列表或标准边界说明。

文件名应简洁、有描述性并直接命名所属概念。仅当模块目录确实需要导航时才使用 `README.md` 或名称清晰的目录页；不要添加空索引或搜索结果中用途不明的 `overview.md` 等通用文件。删除或合并页面时，必须更新所有入站链接，并把独有内容保留到新的权威所有者中。

标题无法明确表达时，文档开头说明目的、所有者或边界以及预期读者。流程前先说明前置条件，先给出最小可运行示例再介绍高级变体，项目专有术语首次出现时定义。相关文档以相对链接放在结尾；设计处于提议、部分实现、废弃或尚未实现时保留简洁状态说明。

文档变更应使新成员能回答：行为位于哪里、如何运行或验证、哪些输入和输出重要，以及哪个相邻文档或源文件是权威。示例必须可运行，或明确标记为示意；绝不包含凭据、用户数据或仅生产环境使用的标识符。

英文文档位于 docs。每个翻译使用 docs_<language> 本地化目录，目录内文件均使用语言后缀。中文目录为 docs_cn，后缀为 _cn。翻译页面必须镜像英文路径、标题、图表、API 名称和内部链接；同时存在时在文档开头附近链接翻译版本。API、配置字段或进程边界变化时，在同一改动中更新英文和本地化页面。

端点和接口的请求、响应使用围栏 json 块。示例保持简单、有效、缩进一致，并仅包含相关字段。其他围栏代码块仅在语法高亮或多行非 JSON 工件确实能提高可读性时使用。

## 契约与首次使用指南

手写接口契约放在负责准入或线上协议的组件下。每个公开字段说明类型、适用单位、用途、默认值或缺省行为、校验与兼容规则。说明调用方、所有者、传输、生命周期、超时、失败结果，以及有效的请求、响应和错误示例。仅属于目标设计的行为标记为 **Target design — not implemented**，并链接可执行的 TODO。

操作指南按首次使用顺序组织：前置条件与设置、包发现与验证、选择与配置、校验与提交、就绪、实时控制与监控、日志与调试，最后是恢复与升级。首次命令之前先介绍相关进程和术语。

## 统一可观测性与发布记录

服务事件使用稳定的事件代码，以及可用的请求与关联标识；时间戳采用 RFC3339 UTC。对有界字段脱敏，不得记录凭据、令牌、原始媒体、提示词、请求原文或无界提供商载荷。记录可处理的状态变化与故障，避免周期性成功噪声。负责聚合或游标读取的服务在所属接口契约中说明保留期和游标轮转后的恢复方式。

应用版本与 API 契约版本独立变化。兼容性扩展保留既有线上字段名和默认值；破坏性变更需要新契约标识和迁移指引。发布说明列出版本与日期、用户可见变化、兼容性与迁移、升级步骤、已知限制及可复现的验证。明确区分已实现行为与目标设计。

## REST API 契约

手写 HTTP 及相关 WebSocket 线协议契约放在 docs/interfaces 下，并与客户端或服务端处理器在同一改动中更新相应契约。

每份契约说明所属边界、认证要求、共享线协议规则、校验限制、成功和错误封装、时间戳与标识符格式及路由特有行为。每个路由使用纯文本 `## METHOD /path` 标题；路由标题不使用代码样式。每个路由说明认证、请求体或查询、最小成功示例和错误码。

说明标准封装的例外，包括探针、遗留路由和流式响应。示例使用服务端精确的线协议字段名和错误字符串。客户端作者无需打开服务端代码就应能判断谁可调用、发送什么、成功返回什么，以及哪些状态码表示校验、授权、未找到和服务端故障。

优先为每个路由提供一个最小请求和响应示例，不用重复字段的表格。相关领域在底部用相对链接交叉引用。不同模型保留在各自文档并相互链接，不要合并术语。

## 代码风格与编辑器设置

使用两空格缩进、禁止 Tab、仓库 rustfmt 配置和 100 列目标。函数保持聚焦，文件按职责拆分；显式类型在确实提升可读性时优先使用。

仓库配置是唯一事实来源。格式化、lint 和缩进设置提交在根目录，并由 CI 强制执行。编辑器和编码助手使用相同仓库配置，不维护第二份风格指南。

## Rust

遵循 [Rust Style Guide](https://doc.rust-lang.org/style-guide/)，再遵循仓库配置。使用 `//!` 说明有价值的模块级约束，使用简短 `///` 说明非显而易见的公开契约。

进程边界使用带上下文的 `anyhow`，库错误使用 `thiserror`。优先使用 Result 而非 panic；传播失败时使用 context。测试之外避免 `unwrap` 和 `expect`。

使用 Tokio。不得阻塞执行器线程；阻塞工作使用 `tokio::task::spawn_blocking`。使用结构化 tracing 和 tracing-subscriber，优先使用结构化字段，绝不记录原文、请求内容、凭据、能力令牌、提供商正文或其他秘密。

单元测试放在代码旁的 `#[cfg(test)]` 模块，集成测试放在 tests。为非平凡行为和容易出错的逻辑增加测试；测试名使用简短的行为描述。

## 仓库与文档

Transnet 保持为一个 Cargo package：Rust 在 src，集成测试在 tests，配置在 config，手写文档在 docs。文件名简短、描述性强并尽量唯一；不要使用重复的通用名称或重复文档。

系统设计位于 docs/transnet.md，任务指南位于 docs/guides，线上与存储契约位于 docs/interfaces，模块参考位于 docs/reference，Rust API 细节位于源注释和 rustdoc。每份契约和模块关注点只有一个权威归属；其他文档只摘要并链接，不复制正文。

文档必须描述已实现行为，并随公开 API、配置或进程边界变化更新。不提交生成文件、构建产物、日志、运行状态、凭据和编辑器状态；提交 Cargo.lock。

## 验证

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test --all-targets
cargo doc --no-deps
```

## Git

使用 `feat:`、`fix:`、`docs:`、`refactor:`、`test:` 或 `chore:` 开头的简洁 Conventional Commit。分支使用意图前缀和 kebab-case 描述。提交前检查状态和差异，只暂存明确路径，不提交无关修改。
